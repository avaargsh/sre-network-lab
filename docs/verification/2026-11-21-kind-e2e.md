### 曾经失败与修复

首次 E2E Run [44858967769](https://github.com/avaargsh/sre-network-lab/actions/runs/44858967769) 在 DNS 恢复后仍观察到 nameserver `127.0.0.1`，导致 `nslookup` 失败。定位到脚本使用 `.items[0]` 选择 Probe Pod：Deployment rollout 结束后旧 Pod 可能仍在 Terminating 状态。之后改为只选择 **未进入删除流程、Running 且 Ready** 的 Pod，并加入离线回归测试；修复后的 Run 44859214979 验证通过。

## LAB-02：Service targetPort 错配

| 阶段 | PodIP:5678 | ClusterIP:80 | Service FQDN:80 | EndpointSlice |
| --- | --- | --- | --- | --- |
| baseline | PASS | PASS | PASS | 正常监听 5678 |
| fault | PASS | curl exit 7（预期） | curl exit 7（预期） | 端口 5679 |
| recovery | PASS | PASS | PASS | 端口恢复为 5678 |

操作：在专用 `sre-lab-service` 中把 Service `targetPort` 从命名端口 `http` 临时设为 `5679`；应用仍监听 5678，故直连 PodIP 成功而 Service 转发失败。恢复 `targetPort=http` 后三类请求都成功。

## 面试使用边界

可以说：“我设计了 Kubernetes Service 和客户端 DNS 的隔离故障实验，在 Kind 3 节点 v1.37.0 集群中完成 baseline、故障注入和恢复检查，并提交了可复现的 Actions 工作流、测试脚本和证据快照。”

**不能说**：这是生产故障恢复、证明 Cilium/Calico 或全部 Kubernetes 网络路径已经验收、证明可用性提升了某个百分比、证明具备物理 MTU 问题定位能力。后续这些能力必须补独立环境和证据。
